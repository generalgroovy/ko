# Model Proposals

These proposals describe future analysis and control models for the KO II
companion project. They are grouped by implementation size and each proposal has
a distinct purpose so Small 1, Small 2, Mid 1, Mid 2, Large 1, and Large 2 do
not overlap.

## Small Models

| Proposal | Unique aspect | Inputs | Output | Effort |
| --- | --- | --- | --- | --- |
| Small 1: Rule-Based Project Summarizer | No training or heuristics; transforms existing analysis JSON into a readable status card. | `project_analysis.json`, `manifest.json` | Human summary, warnings, pad coverage table | 1-2 days |
| Small 2: Archive Signature Catalog | Identifies repeated project structures by hashes and record shapes rather than pad content. | Project catalog, binary record hashes | Duplicate/similar project clusters | 2-3 days |
| Small 3: Pad Usage Heuristic Model | Scores projects by group balance, sparse pads, repeated sound ids, and empty areas. | Project assignments | Usage score and arrangement hints | 2-3 days |

Recommended first pick: Small 1. It improves day-to-day usability immediately
and uses data already generated by the app.

## Mid Models

| Proposal | Unique aspect | Inputs | Output | Effort |
| --- | --- | --- | --- | --- |
| Mid 1: Controlled Edit Difference Model | Learns byte-field hypotheses only from paired before/after captures of one front-panel action. | Project comparison reports, experiment labels | Candidate field map with confidence notes | 1-2 weeks |
| Mid 2: Session State Timeline Model | Merges app-sent MIDI, observed MIDI, and project snapshots into one chronological state record. | Protocol logs, MIDI state JSON, snapshots | Replayable session timeline | 1-2 weeks |
| Mid 3: Local Library Match Model | Matches archived pad sound ids to backed-up PCM/WAV assets and flags missing content. | Project analysis, device library manifests, metadata CRC/SHA | Completeness report for each project | 1 week |

Recommended first pick: Mid 3. It directly answers whether archived projects
have the local sound content needed for reconstruction or review.

## Large Models

| Proposal | Unique aspect | Inputs | Output | Effort |
| --- | --- | --- | --- | --- |
| Large 1: Protocol Digital Twin | Simulates the known EP-133 file/MIDI protocol for tests without live hardware. | Captured SysEx/MIDI sessions, file-tree snapshots | Deterministic fake device backend | 3-5 weeks |
| Large 2: Multimodal Performance Model | Aligns MIDI arranger events, recorded audio, and project archives to explain a full session. | Arranger JSON, performance clips, WAV captures, project analysis | Session map with timing and source attribution | 4-6 weeks |
| Large 3: Verified Write Planner | Plans future write operations with required backup, preflight checks, read-back verification, and rollback gates. | Device snapshots, bundle manifests, proposed write payload | Blocked/allowed write plan with verification checklist | 5-8 weeks |

Recommended first pick: Large 1. It lowers risk for every future hardware-facing
feature because failure modes can be tested without touching the EP-133.

## Selection Guidance

| Goal | Best fit | Reason |
| --- | --- | --- |
| Make analysis easier to read | Small 1 | Converts existing artifacts into user-facing summaries. |
| Find duplicate or near-duplicate projects | Small 2 | Uses archive fingerprints without guessing semantics. |
| Understand arrangement density | Small 3 | Focuses on musical pad usage rather than protocol bytes. |
| Reverse engineer fields safely | Mid 1 | Requires controlled evidence before naming unknown fields. |
| Reconstruct what happened during a session | Mid 2 | Combines logs and snapshots into time order. |
| Verify backup completeness | Mid 3 | Links project pad references to actual backed-up sounds. |
| Test without hardware | Large 1 | Provides a fake EP-133 protocol target. |
| Explain audio/MIDI/project relationships | Large 2 | Connects generated sound, captured audio, and source project data. |
| Prepare for future writes | Large 3 | Makes safety gates explicit before any persistent device mutation. |
